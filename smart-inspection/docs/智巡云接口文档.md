# 智巡云接口文档

版本：`1.0.0-draft`  
基础路径：`http://localhost:8080/api`  
完整 OpenAPI 原稿：`inspection-server/src/main/resources/static/openapi/zhixunyun-openapi.yaml`  
Knife4j 兼容地址由后端自动将这份 YAML 转换为 JSON，不需要维护第二份契约文件。

## 1. 文档入口与实现状态

后端启动后访问：

- Knife4j：`http://localhost:8080/doc.html`
- Swagger UI：`http://localhost:8080/swagger-ui.html`
- 完整接口契约（YAML）：`http://localhost:8080/openapi/zhixunyun-openapi.yaml`
- 完整接口契约（Knife4j 使用的 JSON）：`http://localhost:8080/openapi/zhixunyun-openapi.json`
- 当前真实代码生成的 OpenAPI：`http://localhost:8080/v3/api-docs`

Knife4j 顶部文档分组：

1. `01-完整接口契约（含规划中接口）`：整个项目的接口设计。
2. `02-当前已实现接口`：由现有 Controller 真实生成，只显示已经能调用的接口。

完整契约中：

- `【已实现】` / `IMPLEMENTED`：已经存在 Controller、Service 和 Mapper，可以实际调用。
- `【规划】` / `PLANNED`：请求和响应契约已经确定，但代码尚未开发，当前调用会返回 404。

## 2. 全局约定

### 2.1 身份认证

`POST /api/auth/login` 无需 Token。其他接口默认携带：

```http
Authorization: Bearer <token>
```

Knife4j 的 Authorize 输入框中只填 `token` 本身，不重复填写 `Bearer`。

### 2.2 统一响应

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

- `code = 0`：成功。
- `code != 0`：业务失败。
- 无响应数据时 `data` 为 `null`。
- 前端不能只判断 HTTP 状态，还要判断业务 `code`。

### 2.3 分页

分页请求统一使用 `pageNum` 和 `pageSize`，页码从 1 开始，`pageSize` 最大为 100。

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "pageNum": 1,
    "pageSize": 10,
    "total": 36,
    "records": []
  }
}
```

### 2.4 时间与枚举

- 日期：`yyyy-MM-dd`，例如 `2026-08-27`。
- 日期时间：ISO 8601，例如 `2026-08-27T18:00:00+08:00`。
- 时区：`Asia/Shanghai`。
- 枚举在请求和响应中传英文编码，前端负责显示中文。

### 2.5 角色

| 编码 | 角色 | 主要权限 |
|---|---|---|
| `ADMIN` | 系统管理员 | 基础资料、计划、派单、验收和全部统计 |
| `INSPECTOR` | 巡检员 | 自己的任务、巡检提交和异常查看 |
| `MAINTAINER` | 维修人员 | 自己的工单、维修处理和相关异常 |

后端必须从 JWT 获取当前用户并进行权限判断，不能相信前端传入的当前用户 ID。

### 3.8 巡检任务管理

| 状态 | Method | Path | 使用者 | 说明 |
|---|---|---|---|---|
| 规划 | GET | `/api/inspection-tasks` | 管理员、巡检员 | 分页查询任务，巡检员仅看自己 |
| 规划 | GET | `/api/inspection-tasks/today` | 巡检员 | 我的今日任务 |
| 规划 | GET | `/api/inspection-tasks/{inspectionTaskId}` | 管理员、负责人 | 任务详情 |
| 规划 | POST | `/api/inspection-tasks/{inspectionTaskId}/start` | 负责人 | 开始巡检 |
| 规划 | POST | `/api/inspection-tasks/{inspectionTaskId}/submit` | 负责人 | 提交完整巡检结果 |
| 规划 | POST | `/api/inspection-tasks/{inspectionTaskId}/cancel` | 管理员 | 取消未开始任务 |

任务状态：

```text
PENDING（待巡检） → IN_PROGRESS（巡检中） → COMPLETED（已完成）
        │
        ├─ 超过截止时间 → OVERDUE（已逾期）
        └─ 管理员取消   → CANCELLED（已取消）
```

提交巡检结果是核心事务接口：

```text
校验任务负责人和状态
→ 保存巡检记录
→ 异常时保存 fault_record
→ 自动创建 work_order
→ 修改设备状态
→ 完成巡检任务
```

任何一步失败都回滚。重复提交或并发提交只有一个请求成功，其他请求返回 HTTP 409。

### 3.11 维修工单

| 状态 | Method | Path | 使用者 | 说明 |
|---|---|---|---|---|
| 规划 | GET | `/api/work-orders` | 管理员、维修人员 | 分页查询工单 |
| 规划 | GET | `/api/work-orders/{workOrderId}` | 管理员、负责人 | 工单详情 |
| 规划 | POST | `/api/work-orders/{workOrderId}/assign` | 管理员 | 派单或未接单前重新派单 |
| 规划 | POST | `/api/work-orders/{workOrderId}/accept` | 被指派维修人员 | 接单并开始维修 |
| 规划 | POST | `/api/work-orders/{workOrderId}/submit-result` | 负责人 | 提交维修结果 |
| 规划 | POST | `/api/work-orders/{workOrderId}/verify` | 管理员 | 验收通过或驳回 |
| 规划 | POST | `/api/work-orders/{workOrderId}/rework` | 负责人 | 驳回后开始返工 |
| 规划 | POST | `/api/work-orders/{workOrderId}/cancel` | 管理员 | 取消未处理工单 |
| 规划 | GET | `/api/work-orders/{workOrderId}/operations` | 管理员、负责人 | 工单操作时间线 |

工单主状态机：

```text
PENDING_ASSIGNMENT（待派单）
→ PENDING_ACCEPTANCE（待接单）
→ PROCESSING（处理中）
→ PENDING_VERIFICATION（待验收）
→ COMPLETED（已完成）

PENDING_VERIFICATION → REJECTED（已驳回） → PROCESSING（返工）
PENDING_ASSIGNMENT / PENDING_ACCEPTANCE → CANCELLED（已取消）
```

所有状态动作都必须同时校验：当前用户角色、是否为负责人、前置状态和数据库实际受影响行数。不能只执行 `update status = ?`。

## 6. 开发时如何使用这份契约

每开发一个功能，只从完整契约中取当前接口对应的请求 DTO、响应 VO、角色和状态规则，再按“需求 → 数据库 → API → 调用链 → 编码 → 测试”逐步实现。接口尚未实现时不要创建空 Controller 返回假数据；完成后将 OpenAPI 中的 `x-implementation-status` 从 `PLANNED` 改为 `IMPLEMENTED`，并让当前代码生成文档与完整契约保持一致。
